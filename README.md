# BrainShard — research парсинга контента (ИИ дробление на модули/уроки)

Скрипт прогоняет PDF-книгу/статью через ЗАКРЕПЛЁННУЮ ПАРУ локальных моделей (через LM Studio):
- **Step1** (структурный сплит на модули/уроки) — более сильная модель, которой нужно
  понимать документ целиком и держать сложный формат ответа (JSON).
- **Step2** (конспект/лёгкая перефразировка каждого уже нарезанного урока) — модель
  попроще, задача локальная и не требует держать в голове весь документ.

Пара моделей задаётся один раз в `src/models.config.ts` (константы `STEP1_MODEL` и
`STEP2_MODEL`) — по умолчанию Step1 = `gemma-4-e4b`, Step2 = `qwen3-1.7b`. Чтобы
попробовать другую пару — просто поменяй эти две константы в конфиге.

## Быстрый старт

1. Установи зависимости (один раз):
   ```
   npm install
   ```

2. Открой LM Studio → вкладка Developer → Start Server.
   По умолчанию сервер поднимается на `http://localhost:1234`.
   Если порт другой — поменяй `LM_STUDIO_BASE_URL` в `src/models.config.ts`.

3. Проверь, что `STEP1_MODEL` и `STEP2_MODEL` в `src/models.config.ts` совпадают
   с реальными id в LM Studio. Скрипт сам покажет список доступных моделей при
   запуске и явно предупредит, если одна из двух моделей не найдена в LM Studio —
   в этом случае поправь `modelName` в конфиге.

4. Положи PDF-файл в папку `input/`.

5. Запусти:
   ```
   npm run run -- имя-файла.pdf
   ```
   Один прогон = один документ через закреплённую пару Step1/Step2.
   Чтобы попробовать другую пару моделей на том же документе — поменяй
   `STEP1_MODEL`/`STEP2_MODEL` в конфиге и запусти ещё раз; результаты не
   перезатрутся (см. структуру вывода ниже).

## Что получится на выходе

Всё сохраняется в `output/<имя_документа>/<step1_id>__<step2_id>/`:

```
output/
  _all-runs-summary.md          <- накопительная таблица по ВСЕМ прогнанным документам
  _all-runs-summary.json        <- то же самое, но для программной обработки
  моя-книга/
    gemma-4-e4b__qwen3-1.7b/
      metrics.json               <- все цифры по этому прогону
      step1-raw-response.txt     <- сырой ответ Step1-модели на структурный сплит (смотреть глазами)
      combined-conspect.md       <- все уроки одним файлом подряд
      lessons/
        01-Основы-алгебры/
          _module.md              <- оглавление модуля со ссылками на уроки
          01-Введение-в-переменные.md
          02-Линейные-уравнения.md
        02-Основы-алгебры-(часть-2)/   <- появляется, если в модуле было 15+ уроков
          _module.md                    (см. "Разбиение перегруженных модулей" ниже)
          01-...
        03-Геометрия/
          _module.md
          01-Треугольники.md
    gemma-4-e4b__qwen2.5-7b-instruct/
      ... появится, если позже прогонишь тот же документ с другой парой моделей
```

Каждый файл урока начинается с HTML-комментария с метаданными (кол-во слов в
источнике/результате, попал ли конспект в целевой диапазон 500-800 слов) — это не
видно при рендере markdown, но полезно при просмотре сырого файла.

## Как читать результаты research

1. Открой `output/_all-runs-summary.md` — там одна строка на каждый прогон
   (документ + пара моделей), сразу видно:
   - смог ли Step1 вообще вернуть валидный JSON (`Step1 OK`)
   - сколько модулей/уроков нашёл
   - какой % маркеров успешно резолвился в реальный текст (`Markers resolved`,
     `Avg marker score`) — низкий score означает, что модель "придумывает" маркеры,
     а не копирует их дословно из текста
   - сколько конспектов уложилось в требуемые 500-800 слов
   - сколько было ошибок

2. Если Step1 упал или markers resolved низкий — открой `step1-raw-response.txt`
   внутри папки конкретного прогона и посмотри глазами, что модель реально вернула
   (частые причины: JSON обёрнут в поясняющий текст, модель перефразирует маркеры
   вместо копирования, ответ обрезан по лимиту токенов).

3. Если Step1 в порядке, но конспекты плохие — смотри файлы уроков в `lessons/`.

## Разбиение перегруженных модулей

Если модель в рамках Step1 запихнула в один модуль больше 15 уроков — это
считается технической перегрузкой (по договорённости), и модуль автоматически
режется на части: `Название модуля (часть 1)`, `(часть 2)` и так далее, каждая
часть — не более 15 уроков. Это чисто техническое разбиение (для комфортной
навигации по папкам), а не решение модели о том, что это разные темы — поэтому
заголовок исходной темы сохраняется, дописывается только суффикс "(часть N)".

Порог легко поменять — переменная `MAX_LESSONS_PER_MODULE` в `src/moduleSplitter.ts`.

Метрики `overloaded_modules_split` и `modules_after_split` в `_all-runs-summary.md`
показывают, сколько раз это сработало — полезно для research-вывода о том, как часто
Step1-модель вообще склонна создавать один гигантский модуль вместо нескольких логичных.

## Важное про Step1 на больших документах (28+ страниц)

Сейчас весь текст документа отправляется в модель ЗА ОДИН ВЫЗОВ на Step1 (без
предварительного чанкинга по объёму) — это осознанное решение для первой волны
research: важно самим увидеть, на каком объёме конкретная модель начинает
деградировать (терять маркеры, обрезать ответ, путать структуру), а не
подстраховываться заранее. Метрики `avg_marker_score` и `step1ParsedOk` в
сравнении по разным по объёму документам — это и есть ответ на вопрос
"сколько текста модель реально тянет за один проход".

Если на практике окажется, что все модели стабильно сыпятся уже на 5-10
страницах — тогда есть смысл добавить map-reduce чанкинг (сначала грубое
дробление по кускам текста, затем слияние). Это отдельный шаг, который стоит
делать после того, как будут собраны данные по деградации на текущей схеме.

## Известные ограничения текущей версии

- Fuzzy-поиск маркеров (`src/markerResolver.ts`) использует посимвольный
  Levenshtein — хорошо переживает опечатки и мелкие изменения пробелов/пунктуации,
  но плохо переживает **перестановку слов** внутри маркера (модель написала
  маркер своими словами вместо дословной копии). Если в реальных прогонах
  это окажется частым — надо будет добавить word-level метрику (например Jaccard
  по токенам) как fallback.
- Медиа-контент (картинки, видео) сейчас не обрабатывается — по договорённости,
  первая волна research идёт по чисто текстовым PDF.
- Валидация "конспект уложился в 500-800 слов" — по словам через пробел,
  довольно грубая метрика (не учитывает формулы в LaTeX как отдельные "слова"
  корректно) — но для сравнения моделей между собой этого достаточно.

## Структура проекта

```
src/
  types.ts             — все TypeScript-типы пайплайна
  models.config.ts     — STEP1_MODEL / STEP2_MODEL (закреплённая пара) + base URL сервера
  lmStudioClient.ts     — HTTP-клиент к LM Studio (/v1/chat/completions, /v1/models)
  extractPdf.ts         — извлечение текста из PDF (pdf-parse v2 API)
  jsonExtract.ts        — устойчивый парсинг JSON-ответа модели (снимает ```json обёртки и т.д.)
  markerResolver.ts     — fuzzy-поиск start/end маркеров урока в исходном тексте
  moduleSplitter.ts     — авто-разбиение модулей с 15+ уроками, присвоение индексов
  runner.ts             — сборка полного пайплайна: Step1 (step1Model) → resolve → Step2 (step2Model)
  index.ts              — CLI entrypoint, сохранение файлов и отчётов
prompts/
  step1-structural-split.md  — системный промпт для структурного дробления (JSON, без переписывания текста)
  step2-conspect.md           — системный промпт для конспекта одного урока (твой исходный промпт)
input/                 — сюда кладёшь PDF-файлы для теста (папка не в git, если добавишь .gitignore)
output/                — сюда пишутся все результаты прогонов
```

## Тонкости окружения (на будущее, если будешь переносить проект)

- Проект использует `tsx` для запуска TypeScript, а не `ts-node` — на момент
  сборки `ts-node@10.9.2` оказался несовместим с `typescript@7.0.2` (падал на
  внутреннем API компилятора). Если будешь обновлять зависимости и вернёшься
  к более старому TypeScript — можно спокойно использовать любой раннер.
- `pdf-parse` версии 2.x имеет полностью другой API, чем классическая v1
  (класс `PDFParse` с методом `.getText()` вместо функции `pdf(buffer)`).
  Если в `package.json` увидишь другую major-версию pdf-parse — проверь API
  перед тем, как что-то менять в `extractPdf.ts`.
